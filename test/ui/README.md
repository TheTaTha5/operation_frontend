# เทส UI — เปิดแอปจริงในเบราว์เซอร์แล้ววัด

ชุดนี้แทนฮาร์เนสเดิมที่เคยอยู่ใน `/tmp/w` ของเครื่องพัฒนาเครื่องเก่า และหายไปพร้อมเครื่องนั้น
(`STATUS.md` §5 เขียนเตือนความเสี่ยงข้อนี้ไว้ก่อนแล้ว แล้วมันก็เกิดขึ้นจริง) — คราวนี้อยู่ในรีโป

## ติดตั้งครั้งเดียว

```bash
PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD=1 npm ci
```

ใช้ Google Chrome ที่ติดตั้งในเครื่องอยู่แล้ว (`channel:'chrome'`) จึงไม่ต้องโหลด
browser ของ playwright ~150MB · `node_modules` ประมาณ 18MB

## รัน

```bash
npm run test:ui          # ทั้งสองตัว
npm run test:smoke       # เปิดครบทุกหน้า ไม่มีหน้าไหนพัง
npm run test:mobile      # จอมือถือ ทุกหน้ายังเหลือที่ให้อ่าน

LAD=allotment_v2/data_exports/<subset>.json npm run test:daydetail -- 2026-09-17
```

`test:daydetail` เป็นเทสเฉพาะเรื่อง ไม่ใช่เทสกวาดทั้งแอป — ต้องมีข้อมูลจริงถึงจะมีความหมาย
(ไม่ใส่ `LAD` ข้อมูล seed ไม่มีใบจองของวันไหนเลย ทุกตัวเลขเป็น 0 แล้วมันจะ "ผ่าน" แบบไม่ได้ตรวจอะไร)

ผ่าน = พิมพ์ `พัง 0` และ exit code 0

ใช้เวลาราว 1 นาทีต่อรอบจอ (67 หน้า × ~0.4 วิ) · `test:ui` วัดสองขนาดจอจึงราว 2–3 นาที
รันก่อน deploy ทุกครั้งตาม `HANDOFF.md` §4d ไม่ใช่รันทุกครั้งที่แก้โค้ด

## ใส่ข้อมูลจริง

ไม่ใส่อะไร = ใช้ข้อมูล seed จาก `DEFAULT_*` ทุกหน้าเปิดได้ แต่ตารางสั้น
ปัญหาหลายอย่างโผล่เฉพาะตอนตารางยาว จึงควรรันด้วยข้อมูลจริงด้วย:

```bash
LAD=allotment_v2/data_exports/backup_2026-09-14_1355.json npm run test:smoke
```

⚠ `localStorage` รับได้ราว 5MB แต่ blob จริงราว 19MB — ต้องย่อก่อน
เอาเฉพาะเดือนที่จะตรวจก็พอ (bookings + trips ของเดือนนั้น + boats/vehicles/agents)
ไฟล์ที่ย่อแล้วต้องวางใน `allotment_v2/data_exports/` ซึ่ง gitignore ไว้ — **เป็นข้อมูลลูกค้าจริง ห้ามหลุดเข้า repo**

## ทำไมต้องมีสองตัว

| | จับอะไร |
|---|---|
| `t_smoke` | หน้าเปิดไม่ขึ้น / โยน error / วาดออกมาว่างเปล่า |
| `t_mobile` | หน้าเปิดได้ปกติ **แต่มองไม่เห็นข้อมูล** |
| `t_daydetail` | ป๊อปอัป "รายละเอียดทั้งวัน" ขึ้นตัวเลขคนละชุดกับการ์ด Live bookings |

`t_daydetail` อยู่คนละชั้นกับสองตัวบน · มันไม่ได้ถามว่า "หน้าเปิดได้ไหม" แต่ถามว่า
**"ตัวเลขที่เห็นมาจากกฎเดียวกับที่หน้าอื่นใช้หรือเปล่า"** — คิดค่าที่ควรจะเป็นจาก
`SB_BOOKINGS` ในหน้าเดียวกันด้วย `laIsB2C` + `_dashBkDay` + `acctBookingTotal`
แล้วเทียบกับเลขที่ป๊อปอัปแสดงจริง · **ยืนยันแล้วว่าพังได้จริง**: สลับเกณฑ์วันไปใช้
`bookingDate` แทน `_dashBkDay` แล้วรัน ได้ `พัง 4` (B2B 22 → 17 ใบ · ใบที่คีย์ย้อนหลัง 5 ใบหายไป)

`t_mobile` มีเพราะบั๊ก `§mobUnstick` (2026-09-14): คอลัมน์ข้างและแถบหัวที่ออกแบบไว้
สำหรับจอกว้างเป็น `position:sticky` ที่ไม่มี breakpoint ปลดบนจอแคบ พอจอแคบ layout
ยุบเป็นคอลัมน์เดียว มันไปกองบนสุดแล้วยังตรึงอยู่ สูง 250–750px บนจอ 812px
ข้อมูลข้างล่างเลื่อนลอดอยู่ข้างหลัง **เลื่อนเท่าไหร่ก็ไม่เห็น**

พังแบบนี้ไม่มี error ให้จับ หน้าเปิดได้ปกติทุกประการ `t_smoke` จึงมองไม่เห็น
ต้องวัดพื้นที่ว่างที่เหลือบนจอเอา — วัดตอนเลื่อนลงล่างสุด แล้วรวมความสูงของ
`sticky`/`fixed` ที่ทับกัน (merge ช่วง ไม่ใช่บวกตรง ๆ)

เกณฑ์: เหลือที่อ่าน ≥ 60% ของความสูงจอ · ล้นแนวนอน ≤ 4px
วัดสองขนาด — `390×812` (แถบ URL ยุบ) และ `390×664` (แถบกางอยู่ เตี้ยกว่า เห็นปัญหาชัดกว่า)

**ยืนยันแล้วว่าเทสนี้พังได้จริง**: ย้อน `02-skins.css` กลับไปก่อนแก้ `§mobUnstick`
แล้วรัน ได้ `พัง 15` (7–8 หน้า × 2 ขนาดจอ) แย่สุดคือ `piercheckin` เหลือที่อ่าน 2%

## ยังไม่มี

`t_vals` — เทียบชุดตัวเลข (ราคา/ยอดคน/ยอดรวม) กับค่าฐาน เพื่อจับว่าการแก้ไป
ทำตัวเลขหน้าอื่นเพี้ยนไหม `HANDOFF.md` §4d เรียกหาไว้แต่ยังไม่ได้เขียนใหม่
ตัวนี้สำคัญกว่า `t_smoke` สำหรับงานที่แตะการคำนวณเงิน

## ข้อจำกัดที่รู้อยู่

- รันบน Chrome เท่านั้น จับพฤติกรรมเฉพาะของ iOS Safari ไม่ได้ — โดยเฉพาะ
  `100vh` ที่นับรวมแถบ URL (ดู `§iosDvhModal`) เพราะ Chrome ให้ `dvh` เท่ากับ `vh`
  ส่วนนั้นต้องเปิดบนเครื่องจริงดูเอง
- static server ไม่มี `/api` จึงไม่ได้ทดสอบเส้นทาง login / sync / เขียนลงฐานข้อมูล
  ต้องการของพวกนั้นให้ใช้ `npm run dev:local` แทน
